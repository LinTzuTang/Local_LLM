# 模擬導入：示範精密工業（虛構）的地端 AI 路線圖

> 情境為虛構：台灣中型精密零組件製造暨貿易公司，約 300 人，部門包括業務、生產、研發、品保、採購、倉儲、客服、人資、財務、資訊。公司資料以 `./scripts/start_db.sh` 建立的 PostgreSQL 模擬。
>
> 本文依 2026-10-12 的公開資料整理。標示「待查證」的項目只有二手來源，正式採用前請回到原始文件確認。

## 為什麼選擇地端

- **資料不出公司**：客戶名單、報價、薪資、工單內容都不能送進公有雲 AI。
- **成本可預期**：用一次性的硬體成本，取代按 token 計費。
- **合規**：符合個資法、客戶 NDA 和內部資安政策。

代價是要自己維護硬體、模型更新、評測和資安，而且品質上限受硬體限制。

## 權限設計：這個平台示範了什麼

**讓 AI 看不到不該看的，不能只靠 prompt。**

| 控制層 | 平台做法 | 示範方式 |
| --- | --- | --- |
| 資料庫角色 | 每個 agent 用自己部門的 PostgreSQL 角色連線；薪資、成本等欄位只授權給特定角色 | 業務部助理問「每個人的月薪」→ 回答「沒有權限」 |
| 唯讀＋逾時 | 角色只有 SELECT 權限、交易預設唯讀、查詢 5 秒逾時 | 寫入或耗時查詢會被資料庫拒絕 |
| 工具可見度 | 不允許連網時，外部工具根本不會交給模型 | Agent 側欄的「允許連網工具」開關 |
| 人工核准 | 每次外部呼叫前暫停，顯示即將送出的參數，可核准、修改或拒絕 | 研究助理查天氣、維基百科 |
| 次數上限 | 每個外部工具每次任務最多 N 次（程式強制） | 側欄設定 |
| 內網防護 | 抓網頁工具擋掉 localhost、內網、雲端 metadata 位址 | 防止被注入的網址打到公司內部系統 |
| 稽核 | 每次執行存成 JSON：提示、每次 LLM 呼叫、工具參數與結果、核准決定 | 「📜 紀錄」頁 |

**尚未做到、正式導入前必須補上的：**
- 使用者登入與群組權限，目前角色是依 agent 決定，不是依登入者。
- RAG 文件的權限過濾，必須在檢索時依權限過濾，不能只在介面上隱藏。
- 文件與工具回傳內容中的提示注入防護和測試。
- 用量上限與儀表板。

## 常見陷阱

1. **RAG 外洩**：沒做段落層級的權限控管，薪資或人事文件被不該看的人問出來。
2. **間接提示注入**：惡意指令藏在 email、PDF 或網頁裡，透過工具結果進到模型。
3. **給 agent 寫入權限**：下單、改 ERP 一定要人工核准。
4. **沒有評測集**：只憑「感覺不錯」就上線，換模型時無從比較。
5. **硬體估錯**：真正決定硬體需求的是同時使用人數，不是模型大小。30B 模型 4-bit 約 20GB，另外還要加上 KV cache。
6. **繁簡混用**：模型輸出夾雜簡體字，需要評測並在 prompt 中約束。
7. **影子 AI**：員工私下使用公有雲 AI，要提供好用的內部替代方案，並配合規範。
8. **試點範圍太大**：先求一個部門真的好用，再擴大。

## 治理框架

| 框架 | 用途 |
| --- | --- |
| NIST AI RMF 1.0＋生成式 AI 剖析（NIST AI 600-1） | 風險登錄表的骨架 |
| ISO/IEC 42001:2023 | 可驗證的 AI 管理制度，可與既有 ISO 9001／27001 整合 |
| OWASP Top 10 for LLM Applications、OWASP Top 10 for Agentic Applications | 提示注入、權限過大等威脅模型（最新版本號待查證於 genai.owasp.org） |
| 人工智慧基本法 | 依二手來源整理：2025-12 三讀、2026-01 施行，屬框架性法律，主管機關為國科會（待查證） |
| 數位發展部 AI 風險分類框架 | 用例風險分級（依二手來源，待查證於 moda.gov.tw） |
| 行政院所屬機關使用生成式 AI 參考指引 | 公部門適用，可作為企業 AUP 範本：機密資料不得輸入外部生成式 AI、最終判斷由人負責 |
| 金管會金融業運用 AI 指引 | 非金融業不受拘束，但可作為控制項檢核表 |
| 個人資料保護法 | 對人資與客戶資料做 RAG 時的法遵依據 |
