怎麼看這份研究

這是 31 個具體版本／checkpoint 的代表性清單，涵蓋已成熟的基線與查核日可取得的新模型；不是所有模型的全集，也不是宣稱某款模型絕對最好。每個項目附官方模型卡、權重列表、授權標記和下載指令。模型支援能力來自官方說明；硬體定位與選型順序是本專案的規劃推論，尚未全部實測。

「開源」常被混用：可下載權重（open weights）、Apache/MIT 等權重授權、訓練程式和資料公開，是不同層次。Llama 3.x、Gemma 3／FunctionGemma、Nemotron 使用專屬條款；Gemma 4 的這些 checkpoint 標記 Apache 2.0，不能沿用 Gemma 3 的授權假設。派生模型也要看 base license：例如 R1-Distill-Qwen 的卡片標記 MIT，並說明原始 Qwen2.5 的 Apache 2.0 來源。具體用途應以各 checkpoint LICENSE 原文為準。

LangChain 是應用／agent 框架；Ollama、vLLM 是模型 serving。替換 adapter 只解決 HTTP／訊息介面，不保證兩個 backend 的採樣、工具 parser、量化與品質相同。

記憶體與量化：先算總參數

表中的 GB 是十進位「純權重理論下限」：BF16≈參數量×2 bytes，理想 4bit≈參數量×0.5 bytes。它不是下載大小，更不是完整 runtime RAM/VRAM。實際需要 scale/metadata、未量化層、KV cache、工作 buffer、vision encoder、runtime 與系統記憶體。Embedding／reranker 未必有合適 4bit runtime，表中的下限不能當成現成部署格式。

MoE 的 A3B/A12B 是每個 token 啟用的參數量。通常必須儲存全部 experts，記憶體不能按 active 參數算。30B-A3B 的理想 4bit 下限約15GB，不是1.5GB。671B 與284B 的理想4bit下限已分別約335.5GB／142GB，超過單台 Spark 的128GB統一記憶體。

Spark 的 128GB unified memory 共用 CPU/GPU。初始規劃可為系統和其他服務預留15–25GB（本專案的保守估算），由8K context及低併發起步再量測。NVIDIA recipe 亦採用0.7 GPU utilization；長到256K/1M token時，模型宣稱的上限與實際可用 context 可能差很大。

格式也不能混用：GGUF Q4_K_M、AWQ/GPTQ、FP8、NVFP4、MXFP4是不同格式／kernel路徑；vLLM通常使用HF checkpoint，Ollama常使用GGUF。gpt-oss官方部署說明的20b約16GB、120b約60GB+是特定MXFP4路線，仍需額外記憶體與相容kernel。OpenAI來源。

按用途選模型

  • 輕量／邊緣：先驗證API、prompt、工具schema與速度，降低迭代成本；不以小模型一次答對代表production可靠。
  • 通用／中文 Agent：偏重繁中、指令遵循、參數抽取與長流程成功率，推薦建立Qwen及另一家模型的對照。
  • 程式碼／Coding Agent：要評估repo定位、工具使用、修改驗證與跨檔案任務；單純寫函式的分數不等於整個agent完成率。
  • 推理：thinking token會增加延遲；要配reasoning parser及輸出預算，不能一律用小max_tokens或關閉thinking做公平評比。
  • 視覺：圖片、影片、音訊是否支援取決於具體checkpoint與serving；本次demo只測文字，不宣稱驗證視覺能力。
  • RAG：embedding負責召回，reranker負責重排，聊天模型負責生成；三者不是替代關係。現有search_models只是本機關鍵字檢索。
  • 工具路由／開放研究：FunctionGemma用於專門工具路由；OLMo便於研究訓練流程。需求不同時不應拿通用聊天品質當唯一指標。

評測與已完成 demo

本機實測已保存至專案 runs/：chat.json、agent.json、catalog-agent.json、validation.json。計算任務確實有calculator tool call和ToolMessage，最終答案711；清單查詢確實有search_models tool call。這些是少量integration smoke tests，不是模型benchmark。

小模型第一個無背景問題曾把「地端LLM」誤解成地圖模型；翻譯及受約束工具任務成功。保留這項觀察，避免把只會回應API當成語意可靠。

正式評測至少包含：繁中用語、工具schema/參數正確率、工具錯誤恢復、重複／迴圈、RAG來源忠實度、模型幻覺、多步完成率，以及TTFT、decode tokens/s、總延遲p50/p95、不同context與併發的記憶體。不要直接混用不同量化、prompt、thinking預算的公開benchmark。
